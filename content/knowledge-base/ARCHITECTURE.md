# Архитектура базы знаний «Пора в Аргентину»

Документ описывает структуру базы знаний как **единого источника данных** для сайта goargentina.ru: как устроена иерархия, как её потребляют функции сайта (меню, хлебные крошки, блог, путеводитель, FAQ, поиск, ИИ-консультант) и как безопасно добавлять новые материалы без перестройки структуры.

Снимок на 2026-07-20: **689 исходных записей**, из них **71 проходит усиленный публичный gate**. Манифест не содержит ошибок парсинга, дублей id и битых wiki-ссылок; 618 записей остаются в карантине, а 162 исходные записи не имеют входящей связи. Машиночитаемые артефакты — в `_index/` (`manifest.json`, `manifest.csv`, `navigation.json`, `validation-report.md`), пересобираются `python3 _index/build_manifest.py`.

---

## 1. Модель данных

Одна запись = один файл `.md` = одна сущность. Структура файла: YAML-frontmatter (машиночитаемые поля) + тело на русском. Полная спецификация полей — в `SCHEMA.md`, контролируемые словари — в `TAXONOMY.md`.

**Типы сущностей** (`type`): `attraction` (383), `guide` (98), `faq` (60), `city` (49), `national_park` (44), `author_tip` (29), `transport` (11), `region` (8), `route` (7).

Тип `guide` детализируется полем `subtype` (иммиграция, финансы, культура, планирование, медицина, связь, жильё, безопасность, быт, климат, покупки, природа) — subtype задаёт папку и тематический раздел.

---

## 2. Три уровня навигации

База построена по модели **«хабы → разделы → записи»**, что даёт сайту готовую иерархию.

### Уровень 1 — Разделы сайта (site_sections) = верхнее меню

Канонический словарь из **7 разделов** (поле `site_sections`, у записи их может быть 1-2). Это и есть пункты главного меню:

| Раздел (site_section) | Название в меню | Записей |
|---|---|---|
| `puteshestviya-po-argentine` | Путешествия по Аргентине | 177 |
| `goroda-i-regiony` | Города и регионы | 86 |
| `zhizn-v-strane` | Жизнь в стране | 83 |
| `pereezd-v-argentinu` | Переезд в Аргентину | 62 |
| `dokumenty-i-legalizatsiya` | Документы и легализация | 35 |
| `lichnyy-opyt` | Личный опыт | 30 |
| `finansy-i-ekonomika` | Финансы и экономика | 27 |

Готовое дерево «раздел → записи» сайт берёт из `_index/navigation.json` (генерируется автоматически).

### Уровень 2 — Хабы (точки входа)

**8 навигационных хабов** (id по шаблону `gid-*`) — курируемые оглавления, которые ведут пользователя по теме:

- **Journey-хабы (по пути пользователя):** `gid-puteshestvennika` (турист, 10 шагов), `gid-relokanta` (релокант, 6 этапов + особые случаи).
- **Тематические хабы (по субъекту):** `gid-po-dengam`, `gid-po-dokumentam`, `gid-po-zhilyu`, `gid-po-medicine`, `gid-po-transportu`, `gid-po-kulture`.

Все 8 хабов перекрёстно связаны. Хаб — это «страница-раздел» сайта: с неё пользователь и ИИ-консультант попадают в любую профильную запись за 1-2 перехода.

### Уровень 3 — Записи (листья)

Отдельные статьи, привязанные к разделам через `site_sections`, к теме — через папку/subtype, к соседям — через `related` и `[[вики-ссылки]]` в теле.

## 3. Хлебные крошки

Для любой записи крошка собирается детерминированно:

```
Главная → [site_section] → [хаб темы] → [заголовок записи]
```

Пример: `Главная → Переезд в Аргентину → Документы (gid-po-dokumentam) → ВНЖ Аргентины`.

Данные для этого уже есть в каждой записи (`site_sections`) и в `navigation.json` (какой хаб покрывает раздел). Для геозаписей дополнительно работает связка `region_id`/`nearest_city` (город → регион).

---

## 4. Как функции сайта потребляют базу

| Функция сайта | Источник данных | Как строится |
|---|---|---|
| **Главное меню** | `navigation.json` → `sections` | 7 разделов, порядок фиксирован |
| **Хлебные крошки** | `site_sections` + `navigation.json` | раздел → хаб → запись |
| **Категории блога** | `site_sections` + `tags` | раздел = рубрика, теги = метки |
| **Путеводитель** | типы `city`/`region`/`national_park`/`attraction`/`route` + `gid-puteshestvennika` | геосущности с `media`, `coordinates` |
| **Раздел FAQ** | `type: faq`, сгруппировать по `topic` | 59 карточек Q&A |
| **Поиск по сайту** | `manifest.json` (`id`,`title`,`summary`,`aliases`,`tags`) | полнотекст + алиасы (синонимы запросов) |
| **ИИ-консультант** | тело записей + граф `related`/вики-ссылок | RAG: находит запись, подтягивает связанные |

Ключевое для ИИ-консультанта и «не-тупиков»: **у каждой опубликованной записи ≥1 входящая ссылка** (проверяется автоматически, сейчас 0 сирот), и в конце каждой статьи есть блок «Связанные объекты» — то есть после любого материала очевидны следующие.

## 5. Соответствие типов и разделов (карта размещения)

- **Путешествия** → `route`, `attraction`, `national_park`, guide-subtype `planning`/`nature`/`climate`, часть `faq`.
- **Города и регионы** → `city`, `region`.
- **Жизнь в стране** → guide-subtype `culture`/`daily_life`/`communication`/`health`/`safety`/`accommodation`/`shopping`.
- **Переезд** → guide-subtype `immigration`.
- **Документы и легализация** → guide-subtype `immigration` (виза, ВНЖ, DNI, гражданство, апостиль).
- **Финансы и экономика** → guide-subtype `finance`.
- **Личный опыт** → `author_tip`.

Папки базы соответствуют subtype: `dengi/`, `pereezd/`, `kultura/`, `transport/`, `medicina/`, `zhile/`, `svyaz/`, `bezopasnost/`, `byt/`, `klimat/`, `pokupki/`, `priroda/`, `puteshestvie/` + гео-папки (`goroda/`, `regiony/`, `natsionalnye-parki/`, `dostoprimechatelnosti/`, `marshruty/`) + `faq/`, `lichnyy-opyt/`.

**Одиночные папки** (`byt`, `klimat`, `pokupki`, `priroda`, `bezopasnost`) — это не хаос, а **засеянные разделы**: каждая соответствует subtype из TAXONOMY и готова наполняться. Оставлены намеренно — так структура расширяется без переделки.

## 6. Как добавлять новые материалы (масштабирование)

Структура рассчитана на сотни новых записей без перестройки. Процесс:

1. Взять шаблон нужного типа из `_templates/` (`guide.md`, `faq.md`, `city.md` и т. д.).
2. Заполнить по `SCHEMA.md`, выбрать `subtype`/`topic` только из `TAXONOMY.md`, задать `site_sections` только из 7 канонических значений.
3. Положить в папку, соответствующую subtype.
4. Добавить запись в `related` профильного **хаба** и 1-2 соседних записей (чтобы не появилась сирота).
5. Прогнать `python3 _index/build_manifest.py` — он проверит дубли, битые ссылки, сирот и пересоберёт `navigation.json`.

**Что можно добавлять позже (для каждого хаба видно смежные темы):** остаточный бэклог — питание халяль/кошер, «гид как профессия», доступность по конкретным городам, тематические под-хабы при росте раздела. Это точечные ниши, а не структурные пробелы.

**Правило «от простого к сложному»:** тело записи идёт по канону — понятие → как устроено → шаги/инструкции → рекомендации → частые ошибки → факты → связанные объекты. Термины на испанском вводятся с русским объяснением при первом упоминании.

## 7. Целостность (автоматические гарантии)

`build_manifest.py` при каждом запуске проверяет и блокирует деградацию:

- дубли `id`;
- битые ссылки в `related` (форвард-ссылки/опечатки);
- битые `[[вики-ссылки]]` в телах (с поддержкой `[[id|текст]]`);
- **осиротевшие записи** (0 входящих ссылок, кроме хабов и backlog-слотов);
- пустые обязательные поля по типу (`SCHEMA.md`).

Плюс эмитит `navigation.json` — дерево для сайта. Текущий статус: всё по нулям.

## 8. Готовность к сайту — оценка

| Критерий | Статус |
|---|---|
| Меню | ✅ 7 канонических разделов, `navigation.json` готов |
| Хлебные крошки | ✅ детерминированы (раздел → хаб → запись) |
| Категории блога | ✅ через `site_sections` + `tags` |
| Путеводитель | ✅ геосущности с `media`/`coordinates` |
| FAQ | ✅ 59 карточек, группировка по `topic` |
| Поиск | ✅ `manifest.json` + `aliases` (синонимы) |
| ИИ-консультант | ✅ полные тела + граф связей, 0 тупиков |
| Масштабирование | ✅ шаблоны + словари + валидатор-гейт |

**Остаточные ограничения (некритичные):** часть записей с волатильными фактами (курсы, налоги, миграция) намеренно стоит `confidence: medium` с флажками «проверить на официальном источнике + дата» — это фича честности, а не дефект; их актуализация — процесс поддержки, а не архитектуры. Синхронизация с боевым сайтом (`site_id_map`) — отдельный этап интеграции, к структуре базы претензий не предъявляет.

**Вывод:** архитектура масштабируется и уже служит фундаментом сайта, но редакционный архив не завершён. Публичной считается только запись, прошедшая текущий gate; статус `published` в историческом frontmatter сам по себе не доказывает готовность.
