## Проверка серверного создания заявки

- Клиент не передаёт статус, итоговую цену, данные организатора и платёжные служебные поля.
- Запись заявки и резерв мест выполняются одной транзакцией с idempotency key.
- Миграция применена после schema-only backup; тест создания, повтора и конфликта ключа прошёл с rollback.
- Пока production-таблица tours пуста, сервер читает опубликованный канонический каталог проекта; партнёрские оформления изолированы.

## Жизненный цикл заявки

- Канонические переходы статуса вынесены в `booking-state-machine`; интерфейс организатора использует ту же карту.
- Сервер определяет инициатора перехода и отклоняет обратные, терминальные и недоступные для роли переходы.
- Удалена замена полной заявки через PATCH, которая позволяла менять коммерческие и платёжные поля в обход команд.
- Обновление защищено optimistic concurrency по `updated_at`; при параллельной правке сервер возвращает конфликт вместо перезаписи.

## Изоляция production и demo

- Production и staging собираются только в режиме `production`; неверные Supabase, tour-source и demo-seed настройки останавливают сборку.
- Локальный auth provider подключается отдельным build alias только для явно изолированной demo-сборки.
- Публичная карточка организатора отделена от тестового auth-пользователя и не содержит его пароль или контактные данные.
- После production build клиентские чанки проверяются на маркеры локальной авторизации.
- Ошибки удалённого каталога логируются с источником; strict production не переключается на localStorage/TS seed.
