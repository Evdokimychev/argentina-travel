# Product Experience Audit

Дата baseline: 14 июля 2026. Production SHA: `825791230ba8381dfb4fede0fae31df9c5a8b7f9`.

## Метод

- Production smoke: публичные маршруты, health, закрытые dev routes, anonymous history, иконки.
- Реальный браузер: 320x568, 360x800, 390x844, 430x932, 768x1024, 1024x768, 1280x800, 1440x900, 1920x1080.
- Полная route matrix: более 80 публичных, auth и cabinet routes через Playwright UX audit.
- Отдельная проверка ролей: guest, tourist, organizer, admin и multi-role.
- Performance: Lighthouse production sample; итоговые показатели сохраняются в `var/ops/lighthouse-phase2-prod-last.json`.

## Главные выводы baseline

### P0

Открытых P0 не найдено. Production SHA совпадает с main, health зелёный, direct Postgres доступен, dev routes закрыты.

### P1

1. На мобильном поиске авиабилетов кнопка партнёра выходила за правую границу shadow DOM. Страница не показывала горизонтальный scroll, поэтому обычная overflow-проверка не находила дефект.
2. Роли существуют, но рабочее пространство не оформлено как единая серверная модель. Переключение распределено между меню профиля и отдельными кабинетами.
3. Кабинет туриста частично опирается на локальные helpers для dashboard stats и recent bookings. Для Next Best Action нужен серверный источник истины.
4. Главная администратора показывает устройство разделов и общие показатели, но недостаточно явно отвечает на вопрос «что требует внимания сегодня».
5. Organizer shell подключён на уровне отдельных client pages, а не layout. Это создаёт повторный код и риск неодинаковой загрузки.
6. Fresh production Lighthouse: median performance 49/100 при accessibility 97/100. Главная, каталог и блог загружают исходные изображения размером в несколько мегабайт; home LCP 35,4 с, tours 41,9 с, blog 51,1 с в mobile lab profile.

### P2

1. Главная на мобильном длинная: при 390 px высота документа около 5374 px. Первый экран понятный, но после поиска много равнозначных секций.
2. Формулировка «0 туров на площадке и 53 тура партнёров» технически честная, но ослабляет доверие. В интерфейсе нужно вести с общего доступного предложения, а источник объяснять вторично.
3. Кабинеты используют близкие, но не единые заголовки, empty/error/loading states и мобильную навигацию.
4. В admin access errors встречаются технические слова Supabase и `profiles`; владельцу нужен простой текст и отдельные подробности для разработчика.

## Сценарии и приоритеты

| Сценарий | Baseline | Целевое состояние |
| --- | --- | --- |
| Гость выбирает поездку | Каталог и подбор доступны | Один понятный CTA по намерению |
| Турист возвращается | Общий dashboard | Один Next Best Action из серверных данных |
| Организатор начинает день | Набор dashboard cards | Очередь задач по срочности |
| Владелец открывает admin | Метрики и быстрые ссылки | «Сегодня», «Продажи», «Контент», «Платформа» |
| Multi-role user | Отдельные ссылки в profile menu | Active Workspace с безопасным fallback |
| Поиск авиабилетов 320 px | CTA обрезан | Поля и CTA полностью в viewport |

## Ограничения

- Live provider оплаты не включён: принята модель заявки без предоплаты, платёж после подтверждения. UI не должен обещать мгновенную оплату.
- Частоты и расписания рейсов нельзя выдавать за live-данные без лицензированного источника.
- Production-safe role accounts не должны содержать реальные персональные данные и не создаются автоматически без управляемого seed-процесса.
