# Матрица ролей и разрешений

Дата аудита: 2026-07-15
Область: турист, организатор, администратор, редакционные роли, кабинеты, API и RLS.
Метод: статический аудит исходного кода, миграций, state machine и существующих тестов. Проверка с реальными production-аккаунтами в эту задачу не входила.

## Обозначения

- **Да** — право реализовано и есть серверная проверка или RLS.
- **Владелец** — доступ только к собственной сущности.
- **Capability** — право определяется назначенной административной capability.
- **Частично** — UI существует, но модель согласования, серверная защита или тесты неполны.
- **Нет** — право отсутствует или должно быть запрещено.

## Модель аккаунта

Один аккаунт может иметь несколько ролей из `tourist`, `organizer`, `admin`. Поле `active_role` определяет текущий режим, а cookie рабочего пространства переключает интерфейс между `travel`, `organizer` и `admin`. Переключение рабочего пространства проверяется сервером в `/api/auth/workspace`; оно не выдаёт новую роль.

| Действие | Гость | Турист | Организатор | Админ | Проверка |
|---|---:|---:|---:|---:|---|
| Смотреть публичный каталог и контент | Да | Да | Да | Да | Публичные маршруты |
| Войти в личный кабинет путешественника | Нет | Да | Да | Да | Клиентский `ProfileShell`; данные защищаются API/RLS |
| Бронировать, сохранять избранное, оставлять отзыв | Нет/вход | Да | Да | Да | `src/lib/permissions.ts`; конкретные API проверяют сессию и владельца |
| Переключиться в режим путешествий | Нет | Да | Да | Да | `/api/auth/workspace` |
| Подключить роль организатора | Нет | **Да, самостоятельно** | Не требуется | Не требуется | Прямое обновление собственного профиля; DB-триггер разрешает однократное добавление `organizer` |
| Открыть кабинет организатора | Нет | Нет до подключения | Да | Да | Клиентский `OrganizerShell`; API отдельно проверяют роль |
| Переключиться в режим организатора | Нет | Нет | Да | Нет, если нет роли `organizer` | `/api/auth/workspace` |
| Открыть админ-панель | Нет | Нет | Нет | Да | `AdminShell` + загрузка `admin_staff` |
| Переключиться в режим управления сайтом | Нет | Нет | Нет | Да | `/api/auth/workspace` |
| Выдать себе роль `admin` | Нет | Нет | Нет | Нет | `profiles_protect_sensitive_fields()` откатывает самоповышение |

## Состояния и разрешённые переходы

### Бронирование

| Из состояния | Разрешённые переходы | Кто |
|---|---|---|
| `new` | `pending`, `confirmed`, `cancelled` | Организатор/система; турист — только отмена |
| `pending` | `confirmed`, `cancelled` | Организатор/система; турист — только отмена |
| `confirmed` | `completed`, `cancelled` | Организатор/система; турист — только отмена, если бизнес-правила допускают |
| `completed` | Нет | Терминальное |
| `cancelled` | Нет | Терминальное |
| `waiting_payment`, `paid` | Нет в текущей общей state machine | Платёжный lifecycle ведётся отдельно; требуется документированная связка |

### Авторская статья

| Состояние | Действие организатора | Действие редакции |
|---|---|---|
| `draft` | Редактировать, предпросмотр, отправить | Просматривать при наличии права |
| `in_review` | Читать, ожидать решения | Одобрить или запросить изменения |
| `changes_requested` | Исправить и отправить повторно | Оставить понятную причину |
| `approved` | Читать | Запланировать или опубликовать |
| `scheduled` | Читать | Отменить расписание/опубликовать |
| `published` | Читать | Архивировать/создать ревизию |
| `archived` | Нет явного пользовательского восстановления | Восстановить через CMS/revision flow |

### Тур организатора

В типе организатора доступны только `draft` и `published`. Отдельных состояний `in_review`, `changes_requested`, `approved`, `archived` в `OrganizerTourStatus` нет. Модерация существует в соседнем административном контуре, но единая явная state machine тура не оформлена.

## Разрыв с целевой редакционной моделью

Требуемые роли `owner`, `administrator`, `managing_editor`, `editor`, `author`, `fact_checker`, `moderator`, `support`, `organizer`, `analyst` не представлены как самостоятельные типы и пресеты. Сейчас:

| Целевая роль | Статус | Основной разрыв |
|---|---|---|
| owner | Частично | Совпадает с `super_admin`, но нет отдельной неизменяемой роли владельца и re-auth для критичных действий |
| administrator | Частично | Есть `admin` + capabilities, но нет отдельного пресета с ограничением от owner-only операций |
| managing_editor | Частично | `content_editor` одновременно редактирует и публикует; нет four-eyes rule |
| editor | Нет | Нельзя дать edit без publish готовым пресетом, только ручным override |
| author | Частично | Организатор может писать только собственные статьи; отдельного staff-author preset нет |
| fact_checker | Нет | Нет capability и очереди принятия фактов |
| moderator | Частично | `marketplace_manager` шире модератора |
| support | Частично | Есть `support_agent`, но `users.view` потенциально раскрывает больше PII, чем нужно |
| organizer | Да/частично | Роль есть, ownership есть; подключается без обязательного одобрения |
| analyst | Нет | Есть `analytics.view`, но нет пресета и явного запрета PII/export |

## Проверка по слоям

| Контур | UI | Server/API | DB/RLS | Тесты | Итог |
|---|---|---|---|---|---|
| Рабочие пространства | Скрыты по роли | `/api/auth/workspace` проверяет роль | Cookie HttpOnly, не источник прав | Unit для mapping | Хорошо |
| Личный кабинет | Клиентский gate | API проверяют сессию/ownership | RLS по владельцу | Фрагментарно | Частично |
| Кабинет организатора | Клиентский gate и role-connect | Большинство API проверяют роль и владельца | RLS/owner columns зависят от сущности | Нет полного IDOR E2E | Частично |
| Админ-навигация | Фильтрация по capability | Admin API требуют capability | Admin RLS использует `is_admin_with` | Нет полной privilege-escalation матрицы | Частично |
| CMS | `CapabilityGate` | Edit/publish endpoints разделены не везде одинаково | RLS capability-based | Unit есть, role E2E нет | Частично |
| Профиль | UI только своей сессии | Session user | Own-row RLS + sensitive trigger | Есть отдельные unit | Хорошо с оговорками |

## Критичные находки

| ID | Приоритет | Находка | Риск | Рекомендация |
|---|---|---|---|---|
| PERM-001 | P0 | `resolveAdminCapabilitiesWithClient()` выдаёт `*`, если таблица/профиль временно не читаются или у admin нет строки `admin_staff`; service-role путь также выдаёт `*` при отсутствии staff | Fail-open: административный аккаунт без явного назначения получает полный доступ | Fail-closed; создать явную owner/staff запись миграцией; при ошибке возвращать 403, не `*` |
| PERM-002 | P1 | Любой турист может сам добавить `organizer`; DB trigger прямо разрешает однократное повышение до organizer | Обход заявочного/verification flow, доступ к созданию предложений до проверки | Создавать application; выдавать роль только после admin approval; до одобрения давать ограниченный onboarding |
| PERM-003 | P1 | Роль `admin` при регистрации исторически могла зависеть от metadata; актуальная защита должна проверяться отдельным security fix | Потенциальное повышение прав на старых/обходных signup flow | Новая регистрация всегда `tourist`; admin только через доверенный server action и audit log |
| PERM-004 | P1 | Нет целевых ролей editor/fact_checker/analyst и нет разделения `content.edit`/`content.publish` в готовом пресете | Избыточные права и отсутствие независимой проверки публикации | Добавить пресеты и granular capabilities; запретить self-approval важных материалов |
| PERM-005 | P1 | Нет полной автоматизированной матрицы прямых запросов для чужих туров, статей, API-ключей, webhooks и бронирований | Скрытый UI не доказывает отсутствие IDOR | E2E/API tests: owner A, owner B, admin с ограниченной capability, blocked staff |
| PERM-006 | P2 | Общая booking state machine не включает `waiting_payment` и `paid` | Несогласованные статусы между бронью и платежом | Оформить единую спецификацию lifecycle и переходов system/webhook |
| PERM-007 | P2 | Критичные admin-действия не имеют общей политики re-auth/двухэтапного подтверждения | Ошибка оператора или угнанная сессия может изменить staff, flags, redirects | Re-auth для staff/system settings; typed confirm; audit before/after |
| PERM-008 | P2 | Авторская статья имеет полный workflow, а тур организатора — только `draft/published` | Причина отказа и повторная отправка тура не моделируются явно | Ввести tour moderation state machine и журнал решений |

## Mobile UX по ролям

- Все три кабинета имеют отдельный mobile header и bottom navigation; organizer показывает три главных пункта и меню «Ещё».
- Меню профиля на мобильном закрепляется у нижнего края и ограничено по высоте, учитывает safe area и экранную клавиатуру.
- Длинные формы редактора тура имеют отдельную mobile action bar, но требуют E2E-проверки сохранения при открытой клавиатуре, browser Back и восстановлении scroll.
- Админские таблицы и редакторы остаются наиболее рискованными: нужен тест 320/360/390 px на горизонтальный overflow, sticky actions, dialog focus и destructive confirmation.
- Access denied и loading состояния существуют, но сквозные сценарии с недостаточной capability на мобильном не автоматизированы.

## Release verdict

**NO-GO для полномасштабного релиза RBAC**, пока не закрыт PERM-001. Для organizer onboarding необходим продуктовый выбор: мгновенное самостоятельное подключение или проверяемая заявка; текущая реализация противоречит требованию verification. Остальные базовые ownership-проверки присутствуют, но нуждаются в сквозной IDOR-матрице.
