# План отката production-релиза 2026-07

Дата актуализации: 2026-07-15. Цель — восстановить безопасную работу сайта с минимальной потерей данных. Откат приложения и восстановление базы — разные операции; Vercel rollback не отменяет Supabase migration.

## Подготовить до релиза

- Предыдущий стабильный Vercel deployment ID, его commit SHA и время.
- Текущий и целевой Supabase migration ID.
- Свежий `npm run backup:schema` и отдельный backup **данных** Supabase с подтверждённым retention/restore доступом.
- Проверенный на staging forward-fix SQL для каждой рискованной миграции.
- Список затронутых таблиц, совместимость старого приложения с новой схемой и владелец решения.
- Способ временно отключить опасную функцию или включить maintenance. Если его нет, это фиксируется как release blocker для destructive migration.
- Контакты Application owner, Database owner, QA и Security owner в канале релиза.

## Сигналы к откату

Немедленный откат без ожидания полного расследования:

- privilege escalation, обход RLS, утечка PII или секретов;
- неверное списание, двойная оплата/бронь, неидемпотентный webhook;
- массовая невозможность войти, зарегистрироваться или восстановить пароль;
- устойчивые 5xx, недоступность БД, повреждение/потеря данных;
- production SHA/env не соответствуют утверждённому релизу.

Откат либо feature disable по решению coordinator:

- критичный journey не проходит у существенной доли пользователей;
- заметная регрессия latency/ошибок или сбой партнёрской интеграции;
- неверные consent/analytics cookies;
- SEO/контентная ошибка с масштабным индексируемым эффектом.

## Выбор сценария

| Сценарий | Когда применять | Основное действие |
|---|---|---|
| A. Только приложение | Ошибка в коде; новая схема backward compatible | Promote предыдущий стабильный Vercel deployment |
| B. Feature disable | Ошибка локализована; остальной сайт безопасен | Отключить затронутую функцию утверждённым env/flag/maintenance механизмом, затем redeploy при необходимости |
| C. Forward-fix БД | Миграция ошибочна, данные целы, исправление безопаснее восстановления | Применить заранее проверенную новую migration, не редактируя уже опубликованный SQL |
| D. Restore БД | Повреждение/потеря данных или forward-fix недостаточен | Ограничить запись, восстановить данные+схему в согласованную точку, затем совместимое приложение |
| E. Внешняя интеграция | Поставщик оплаты/тура/email нестабилен | Отключить интеграцию/перевести UX в безопасный fallback; не откатывать БД без причины |

## A. Быстрый откат приложения

Целевое время: решение ≤5 минут, восстановление ≤15 минут.

1. Release coordinator объявляет rollback и фиксирует симптомы/время.
2. В Vercel выбрать предыдущий стабильный deployment ID и выполнить **Promote to Production**.
3. Не запускать rebuild старого SHA: Promote сохраняет проверенный артефакт и его build-time `NEXT_PUBLIC_*`.
4. Убедиться, что production domain указывает на старый deployment.
5. Выполнить:

```bash
EXPECTED_GIT_SHA=<previous-sha7> \
SMOKE_BASE_URL=https://www.goargentina.ru \
npm run production-smoke

PLAYWRIGHT_BASE_URL=https://www.goargentina.ru \
npm run test:e2e:smoke
```

6. Проверить auth, booking/checkout и затронутый сценарий вручную.
7. Если старое приложение несовместимо с уже применённой схемой, немедленно перейти к C или D; многократное переключение deployment не исправит БД.

## B. Временное ограничение функции

1. Остановить только небезопасный путь: checkout, role upgrade, sync, email или другой затронутый модуль.
2. Сохранить чтение публичного контента, если оно не затронуто и не раскрывает данные.
3. Изменение `NEXT_PUBLIC_*` требует нового Vercel deployment; server-only env может также потребовать redeploy для предсказуемости.
4. При инциденте cron временно прекратить его side effects или заменить secret/маршрут по утверждённой процедуре; не выполнять ручной cron повторно до проверки идемпотентности.
5. Сообщение пользователю должно быть нейтральным и не обещать успешную бронь/оплату, если операция не завершена.

## C. Forward-fix Supabase

Предпочтительный путь для уже применённой схемы, когда данные не повреждены.

1. Ограничить записи в затронутый модуль.
2. Снять read-only состояние и backup перед исправлением.
3. Создать **новую** migration с более поздним ID; не менять опубликованный файл задним числом.
4. Проверить SQL на staging-копии и выполнить `supabase:verify`, `rls-audit`, auth/RBAC tests.
5. Применить только новую проверенную migration через журналируемый runner. Не создавать baseline и не менять checksum во время аварии; неизвестная или unjournaled production-схема остаётся блокером до отдельной сверки.
6. Сверить `/api/health.migrationVersion`, права, число/целостность строк и затем вернуть запись.
7. Выполнить production smoke и затронутые journeys.

## D. Восстановление Supabase

Использовать только по решению Database owner и coordinator. Schema backup из `npm run backup:schema` **не содержит данные** и сам по себе недостаточен.

1. Включить maintenance или заблокировать записи, зафиксировать точное время инцидента.
2. Определить допустимую точку восстановления и потенциальное окно потери данных.
3. Экспортировать доступные записи после backup point для последующей сверки/досинхронизации.
4. Восстановить production из подтверждённого Supabase data backup/PITR в отдельный проект или по процедуре провайдера; сначала проверить целостность вне live traffic.
5. Применить согласованную схему и RLS; выполнить read-only проверки ролей, бронирований, оплат и CMS.
6. Развернуть совместимый Vercel deployment и только затем вернуть production domain/запись.
7. Повторно обработать события после точки восстановления только идемпотентным способом; отдельно сверить payment provider и bookings.
8. Выполнить полный набор production из `test-matrix.md`.

## E. Интеграции и платежи

- Не повторять webhook или checkout вручную без проверки idempotency key и фактического состояния у провайдера.
- При расхождении payment/booking считать внешний провайдер источником факта платежа, а исправление делать контролируемой reconciliation-процедурой.
- При сбое партнёрского каталога показывать честный fallback и не выдавать устаревшую цену за подтверждённую.
- После восстановления выполнить соответствующий `tripster:verify`, `sputnik8:verify`, `youtravel:verify`, email delivery check или payment sandbox/reconciliation test.

## Проверки после любого отката

1. `/api/health`: ожидаемый SHA, `deployEnv=production`, Postgres и migration ID.
2. `production-smoke`, `test:e2e:smoke`, затем конкретный сломанный journey.
3. Vercel logs: нет продолжающегося всплеска 5xx/timeouts.
4. Auth/RBAC/RLS и privacy, если инцидент связан с пользователями.
5. Booking/payment/email/cron reconciliation, если операции могли быть приняты во время инцидента.
6. Наблюдение не менее 60 минут; решение «стабилизировано» фиксирует coordinator.

## Закрытие инцидента

В журнале сохранить: временную шкалу, симптомы, затронутых пользователей/операции, deployment IDs и migration IDs до/после, команды и исполнителей, результат smoke, оценку потери данных, оставшиеся ручные reconciliation-задачи. До завершения разбора не удалять Vercel logs, test artifacts и backups; повторный релиз создаётся новым SHA и проходит полный `rollout-plan.md`.
