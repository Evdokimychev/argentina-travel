# Аудит поиска и индекса

Дата проверки: 2026-07-15. Среда: локальная ветка `content/knowledge-base-editorial-system`, dev-сервер `http://localhost:3000`.

## Резюме

Поиск уже имеет подходящую основу: единое модальное окно, API, три уровня выдачи (Meilisearch → PostgreSQL → статический индекс), клавиатурную навигацию и аналитику кликов. Во время аудита был найден блокирующий дефект: статический fallback терял все результаты типа `place`. Параллельная реализация добавила `place` в порядок групп и unit-тест; повторный локальный запрос теперь возвращает Игуасу. Остальные разрывы — неполная схема документа/фильтров, слабый freshness-контроль и бесполезный нулевой результат — сохраняются.

Минимальный блокирующий срез:

1. закрепить уже добавленный `place` API-тестом `kind=place` при принудительном static source;
2. закрепить контракт индекса и отсутствие дубликатов/404;
3. индексировать полный очищенный текст, алиасы/транслитерации, регион, намерение и даты проверки;
4. показывать полезное нулевое состояние с исправлением раскладки/опечатки и ссылками на хабы;
5. проверять не только пустой, но и неполный/устаревший PostgreSQL-индекс.

## Фактическая архитектура

| Слой | Реализация | Наблюдение |
|---|---|---|
| Точка входа | `Header.tsx`, глобальный `SiteSearch.tsx`, событие `site-search:open`, `⌘/Ctrl+K` | Кнопка поиска доступна и на мобильном header; дублируется в мобильном меню |
| Клиент | `SiteSearch.tsx`, debounce, отмена предыдущего запроса, локальный fallback | Есть loading, группы, стрелки/Enter/Escape, `aria-activedescendant` |
| API | `/api/search` → `executeSiteSearch` | Проверяет длину запроса и допустимый `kind` |
| Провайдеры | Meilisearch → RPC `search_site_documents` → `searchSiteIndex` | Полезная деградация, но уровни дают разную полноту и релевантность |
| Статический индекс | `/api/site/search-index`, `site-search-index-server.ts` | Используется браузером и fallback API |
| Индексация | `search-indexer.ts` → `search_documents`; затем Meilisearch | Upsert и удаление исчезнувших id реализованы |
| PostgreSQL | `search_documents`, русская `tsvector`, RPC | Нет подтверждённого `unaccent`/trigram для латиницы, диакритики и опечаток |
| Meilisearch | `title`, `body_text`, `description`; фильтр `kind` | Нет полей региона, сезона, намерения, authority и freshness |

Это рабочее состояние включает параллельно добавляемую базу знаний. Ранее зафиксированный релизный baseline — 323 документа без `knowledge`; в нём встречались три повторяющихся навигационных id. Текущая дедупликация устраняет их, но должна быть закреплена тестом, иначе цифра зависит от порядка сборщиков.

Каталоги туров и экскурсий поступают в серверный индекс отдельно и могут отсутствовать в статическом ответе без настроенных партнёрских источников.

## Подтверждённые дефекты

### SEARCH-001 — статический fallback не возвращал места (P0, исправлено в working tree)

На первой проверке `SearchResultType` и UI знали тип `place`, статический индекс содержал 100 мест, но `TYPE_ORDER` в `src/lib/site-search.ts` не содержал `place`. Группа создавалась, затем отбрасывалась при финальной сортировке.

Фактический запрос:

```text
GET /api/search?q=Игуасу&kind=place
200 {"results":[],"source":"static","query":"Игуасу","kind":"place"...}
```

Параллельная правка добавила `place` в `TYPE_ORDER` и тест `keeps place results in the grouped fallback`. Повторная проверка вернула `/places/iguazu-falls` и другие места. Нужен ещё API-тест, принудительно фиксирующий `source=static`, чтобы контракт провайдерной деградации не зависел только от unit-теста функции.

### SEARCH-002 — недостаточная схема документа (P1)

Текущая строка `search_documents` хранит `id`, `slug`, `kind`, `title`, `description`, `body_text`, `url`, `published_at`. Для базы знаний не хватает:

- канонических алиасов, латиницы и транслитераций;
- региона/провинции/города;
- пользовательского намерения (`entry`, `money`, `transport`, `safety`, `itinerary`);
- сезона, длительности и аудитории;
- `updated_at`, `verified_at`, authority источника и статуса публикации;
- отдельных заголовков разделов и краткого ответа для сниппета.

Полный текст теперь может попадать в `searchText`, но клиентский ответ намеренно его удаляет. Это правильно для веса payload, однако серверный контракт и очистка текста должны иметь отдельные тесты.

### SEARCH-003 — неполезный нулевой результат (P1)

Состояние ограничено фразой «Ничего не найдено…». Нет:

- предложения исправить раскладку/опечатку;
- известных алиасов (`Jujuy`/`Жужуй`, `Iguazú`/`Игуасу`, `Ushuaia`/`Ушуайя`);
- снятия слишком узкого фильтра одним действием;
- ссылок на путеводитель, базу знаний, регионы и места;
- события `search_no_results` с нормализованным запросом и выбранным фильтром.

### SEARCH-004 — неполный индекс не самовосстанавливается (P1)

Автовосстановление ориентируется на полностью пустую таблицу. Непустой, но устаревший индекс может продолжать обслуживать выдачу без сигнализации. Нужны версия сборки, ожидаемое количество по типам, время последней успешной индексации и readiness-порог.

### SEARCH-005 — фильтры и ранжирование не отвечают задачам портала (P2)

UI фильтрует только по типу; отдельной кнопки `immigration` нет. Провайдеры не умеют фильтровать по региону, сезону, длительности, формату поездки, доступности без автомобиля и дате проверки. Статическое ранжирование не учитывает authority, свежесть, канонический материал и пользовательское намерение.

### SEARCH-006 — SearchAction ведёт не в единый поиск (P2)

Структурированные данные сайта направляют `SearchAction` на `/tours?query=...`, хотя глобальная поисковая поверхность охватывает контент, места, документы и продукты. Нужен индексируемый URL результата либо осознанное удаление несоответствующего SearchAction.

## Покрытие контента

| Тип | Что индексируется сейчас | Что требуется добавить |
|---|---|---|
| Блог | title, excerpt, category, author, tags, slug; серверный full text добавляется отдельным путём | headings, canonical topic, aliases, verified/source metadata |
| Путеводитель/иммиграция | title, description, section headings и часть текста | intent, audience, authority, verified_at, sensitive-claim state |
| База знаний | manifest + опубликованный контент, полный текст в серверном поле | устойчивый publication contract, aliases, topic/region facets, source authority |
| Регионы | name, intro, region, keywords | все обязательные секции, place relations, season/transport facets |
| Места | name, short description, region/province/city/tags | aliases, official names, полный текст, coordinates/category facets, verified_at |
| FAQ/legal/pages | видимый заголовок и краткий текст | publication status, updated_at, authority; исключение служебных страниц |
| Туры/экскурсии | партнёрские listing fields | availability freshness, location aliases, stale inventory policy |

## Целевой контракт документа

```ts
type SearchDocumentV2 = {
  id: string;
  schemaVersion: 2;
  kind: SearchResultType;
  canonicalUrl: string;
  title: string;
  description: string;
  headings: string[];
  bodyText: string;
  aliases: string[];
  topics: string[];
  intents: string[];
  regions: string[];
  audience: string[];
  season?: string[];
  duration?: string[];
  publishedAt?: string;
  updatedAt: string;
  verifiedAt?: string;
  sourceAuthority?: "official" | "primary" | "editorial" | "partner";
  publicationStatus: "published";
};
```

Клиенту следует отдавать только поля сниппета и фильтров; `bodyText` остаётся серверным.

## Минимальная реализация по приоритету

1. **P0:** сохранить добавленные `place` в `TYPE_ORDER` и unit-тест; добавить API-тест `kind=place` при принудительном static source.
2. **P0:** контрактный тест: уникальные `id` и `href`, URL опубликован, все типы известны, ожидаемый минимум документов по типам.
3. **P1:** единая нормализация (`ё`, диакритика, дефисы, латиница, известные алиасы) во всех трёх провайдерах; fixture-набор RU/ES/EN.
4. **P1:** версия индекса, `indexed_at`, counts by kind, readiness-проверка расхождения и управляемый reindex.
5. **P1:** улучшенное нулевое состояние и `search_no_results`.
6. **P2:** facets и ранжирование по authority/freshness/intent; единый URL поисковой выдачи для SearchAction.
